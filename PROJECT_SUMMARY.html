Solar Cloud Coverage Forecaster

Prévision de production solaire à H+1 → H+48 — couplage imagerie satellite + NWP

Zones : Belgique · Pays-Bas · Nord de la France · Luxembourg · Ouest de l'Allemagne

Mode d'exécution : 100 % local sur le poste d'un membre de l'équipe SPM B2B BE (téléchargement, entraînement et inférence).

1. Vue d'ensemble

Pipeline Python qui combine deux sources de données complémentaires pour produire des prévisions de couverture nuageuse et d'irradiance solaire (GHI) à plusieurs horizons (H+1, H+3, H+6, H+12, H+24, H+48) :

  • Sat24.com (Infoplaza) — tuiles JPEG VIS & IR toutes les 15 min
  • Open-Meteo — variables NWP horaires (couverture nuageuse, GHI, vent, T°, précipitations)

Les images sont transformées en cloud index + vecteurs de mouvement (flot optique) qui alimentent un modèle XGBoost multi-horizons exposé via une API REST FastAPI.

Cible d'exécution — équipe SPM B2B BE

Le projet est local-first : un membre de l'équipe SPM B2B BE peut, depuis son propre poste de travail (Windows, macOS ou Linux), :

  • Télécharger les tuiles satellite dans data/raw/
  • Stocker les métadonnées + features + prévisions dans une base SQLite (data/solar_forecast.db) — aucune installation Postgres ni Docker requise
  • Entraîner le modèle XGBoost en local (CPU suffisant, < 5 min sur 90 j de données)
  • Faire tourner l'inférence et l'API FastAPI sur 127.0.0.1:8000

PostgreSQL/TimescaleDB et Docker restent disponibles en option pour un déploiement partagé, mais ne sont plus la voie par défaut.

Python 3.11 SQLite (par défaut) FastAPI XGBoost OpenCV pvlib Optuna APScheduler PostgreSQL / Docker (optionnels)

Améliorations transversales livrées

  • Improvement A — APScheduler intégré (scheduler/pipeline.py) : un seul process orchestre scrape (15 min), fetch météo (1 h), feature worker (15 min), trigger forecast (1 h).
  • Improvement B — Worker de feature engineering (features/pipeline_worker.py) : balaye les images processed=False, calcule cloud index + flot optique par zone, marque comme traité.
  • Improvement C — Tuning Optuna walk-forward (run_optuna_tuning) : recherche bayésienne sur 9 hyperparamètres XGBoost avec validation glissante 3 folds.
  • Improvement D — Endpoint /health : statut ok / degraded / unavailable selon fraîcheur scrape, météo, présence du modèle, zones avec prévisions récentes.
  • Improvement F — Fallback nocturne automatique : pvlib détecte l'élévation solaire, le canal VIS est sauté la nuit (IR + NWP only).
  • Docker Compose — stack 3 services (TimescaleDB + scheduler + API) avec healthchecks et volumes persistants.

4. Points forts

Séparation des responsabilités

Chaque module (scraper, fetcher, features, modèle, API) est isolé, testable individuellement et orchestré par main.py. Le couplage transite uniquement par la base de données.

Approche multi-niveaux

Baseline flot optique sans entraînement + XGBoost multi-horizons. Le baseline reste utilisable même sans 90 j de données.

Rigueur ML série temporelle

Split temporel strict (jamais de shuffle), évaluation MAE/RMSE/skill vs NWP, walk-forward CV pour le tuning Optuna.

Stockage adapté

TimescaleDB avec hypertables sur captured_at + index par zone — taillé pour des requêtes time-series à grande échelle.

Production-ready

Dockerfile, docker-compose, healthchecks HTTP & DB, retry & cache HTTP côté Open-Meteo, rate-limit côté sat24.

Robustesse opérationnelle

Fallback nocturne basé sur pvlib, scheduler avec max_instances=1 + coalesce=True, gestion d'erreurs au niveau de chaque job.

API claire

FastAPI auto-documentée (/docs), schémas Pydantic explicites, endpoint /health détaillé pour le monitoring.

Configuration centralisée

Tout passe par config.py + .env : URL DB, intervalles, zones, variables NWP, horizons. Aucune valeur magique disséminée.

5. Points faibles

Aucun test automatisé

Pas de répertoire tests/, pas de pytest, pas de CI. Les régressions sur le calcul de cloud index, flot optique ou jointure merge_asof passeraient silencieusement.

Bbox de zones non calibrées

Les ZONE_PIXEL_BBOXES dans pipeline_worker.py sont des placeholders. Tant qu'elles ne sont pas calibrées sur les vraies dimensions des tuiles, les cloud index par zone sont approximatifs.

Ingestion ligne-par-ligne

ingest_weather_dataframe fait un session.add par ligne — non scalable sur de gros backfills (90 j × 8 zones × 24 h ≈ 17 000 lignes). Aucun bulk_insert ni COPY.

Pas de gestion de doublons

Aucune contrainte d'unicité ni ON CONFLICT sur les tables. Relancer un backfill ou un fetch insère des doublons en base.

Mapping API ↔ horizon imprécis

GET /forecast/{zone}/{horizon_h} renvoie systématiquement forecast.forecast[0] au lieu de chercher la ligne au bon valid_at.

Conversion GHI naïve

ghi_pred = ghi_clearsky × (1 − cloud × 0.75) est une formule paramétrique sans validation empirique. À remplacer par un modèle entraîné sur shortwave_radiation.

Couplage circulaire potentiel

scheduler.pipeline importe output.forecast_api.trigger_forecast, qui démarre l'app FastAPI au chargement du module. Risque de double exécution selon l'environnement.

Pas de versioning des modèles

Un seul fichier xgboost_v1.pkl, écrasé à chaque train. Aucun MLflow / DVC / lineage : impossible de comparer deux runs ou de revenir à une version antérieure.

6. Points d'attention

Statut juridique de sat24

L'API tuiles d'Infoplaza n'est pas publique ni documentée. À vérifier impérativement les CGU avant tout usage commercial. Pour de la production, basculer sur l'API officielle Eumetsat SEVIRI/MSG.

Géoréférencement des tuiles

Le mapping pixel ↔ lat/lon repose sur la convention SlippyMap/TMS. La constante TILES dans config.py couvre BE/NL/FR-nord à zoom 5 — à recalibrer pour toute autre zone.

Volume de données requis

Le modèle XGBoost a besoin d'au moins 30–90 jours de scraping continu pour atteindre un skill score positif. La baseline flot optique pallie en attendant.

Secrets en clair dans docker-compose

POSTGRES_PASSWORD: solar_secret est codé en dur. À externaliser via .env + env_file ou un secret manager avant tout déploiement.

Quota Open-Meteo

L'API gratuite Open-Meteo limite à ~10 000 requêtes/jour. Avec 8 zones × cron horaire, ça reste très en-dessous, mais le cache (requests_cache TTL 3600 s) est essentiel.

Concurrence scrape ↔ feature worker

Les deux jobs tournent à 15 min. Si le scrape déborde, le worker peut tomber sur un fichier en cours d'écriture. Acceptable en pratique (Pillow lèvera et le record reste processed=False) mais à surveiller.

Absence d'observabilité

Logs logging standard uniquement, pas de métriques (Prometheus, OpenTelemetry). Le /health est un bon départ mais ne remplace pas un dashboard.

Imports tardifs dans main.py

Les imports lourds (pvlib, xgboost) sont faits dans les fonctions de commande pour démarrer vite. Pratique correcte mais qui complique l'analyse statique.

7. Reste à faire

Court terme — qualité & robustesse

  • À faire Suite de tests pytest : unitaires (cloud index, flot optique, encodage temporel) + intégration (scrape mocké, ingestion DB sur SQLite).
  • À faire Workflow GitHub Actions : ruff + pytest + mypy sur PR.
  • À faire Calibration des ZONE_PIXEL_BBOXES à partir des vraies tuiles (lecture du JSON sidecar + reprojection).
  • À faire Contraintes d'unicité (captured_at, zone_name, channel) + INSERT … ON CONFLICT DO NOTHING dans toutes les fonctions d'ingestion.
  • À faire Bulk insert COPY pour ingest_weather_dataframe (gain ×100 sur le backfill).
  • À faire Corriger GET /forecast/{zone}/{horizon_h} (filtrer par valid_at ≈ now + horizon).
  • À faire Externaliser les credentials DB hors du docker-compose.yml.

Moyen terme — qualité du modèle

  • Important Cible GHI réelle : entraîner un second XGBoost sur shortwave_radiation au lieu de la formule paramétrique.
  • Important Versioning MLflow ou DVC sur les modèles + suivi des métriques par run.
  • Important Lags multi-frame (cloud index t, t-15, t-30, t-60 min) en features.
  • Important Validation hors zone (transfert Bruxelles → Paris-Nord) pour mesurer la généralisation.

Long terme — phase P7

  • P7 ConvLSTM ou TimeSformer sur séquences d'images — nécessite ≥ 90 j de données collectées.
  • P7 Fusion hybride : sortie ConvLSTM en feature additionnelle de l'XGBoost.
  • P7 Migration éventuelle vers EUMETSAT SEVIRI/MSG pour un usage commercial.
  • P7 Frontend de visualisation (dashboard Plotly Dash ou Streamlit) pour exploration interactive.

8. Synthèse

Le projet est un pipeline ML complet et bien structuré qui couvre l'intégralité de la chaîne : collecte → stockage → feature engineering → entraînement → inférence → API. Les phases P1 à P6 et P8 sont livrées, ainsi que cinq améliorations transversales (scheduler intégré, worker auto, tuning Optuna, healthcheck, fallback nocturne).

Les fondations sont solides (architecture modulaire, séparation claire, choix techniques adaptés au time-series), mais le projet souffre de l'absence de tests automatisés et de quelques approximations qui resteront masquées tant qu'il n'y aura pas de vraie campagne de scraping de 90 j. La calibration des bounding boxes pixel et la validation empirique de la conversion GHI sont les deux prochaines étapes critiques pour passer du prototype à la production.
